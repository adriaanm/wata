# 0013 — iroh end to end: device to Mac across real networks

Status: proposed

`[IROH-E2E]`

## Problem

Phase 4 of [0003](0003-parity-and-beyond.md) (as reordered). The iroh
spike proved the Rust sidecar builds and tunnels on the host; nothing
has proven the full path: a BQ268 on a foreign network reaching a
wata-server on the home Mac, surviving roaming and relay fallback.
This is the roadmap's biggest unknown, so it goes first, and its
output is a personal end-to-end setup the family can actually use.

## Shape

Two sidecar roles, one binary (`iroh-tunnel/`, adopted from the spike,
iroh 1.x pinned by its Cargo.lock):

- **serve** (on the Mac): accepts iroh connections whose node id is in
  the allowlist, forwards streams to `localhost:8008` (wata-server).
  The allowlist IS the access story for this sweep: no listening TCP
  port on any interface, no password surface, connections mutually
  authenticated by key. Refinements (invites, rotation) are phase 6.
- **connect** (on the device): maintains the tunnel, exposes
  `localhost:8008` to wata-fb — the client keeps speaking plain HTTP
  to a loopback and needs zero code changes. armv7-musl static
  cross-build (the spike's open question; first milestone).

Provisioning: a JSON config per node (`node key, peer node id, relay`)
generated by a `just iroh-enroll` recipe; QR later, phase 6.

## Milestones (each a commit, in order)

1. `iroh-tunnel/` adopted in-tree, `just tunnel-serve`/`tunnel-connect`
   recipes, Mac-to-Mac loopback E2E (two processes, one machine).
2. armv7-musl cross-build (`cross` or cargo-zigbuild — decide by
   trying; record the choice) + on-device smoke: device on home LAN
   tunnels to the Mac, wata-fb full session over it.
3. Foreign-network E2E: device on a phone hotspot, full walkie-talkie
   round trip; measure and record connect latency, PTT-to-played
   latency, and relay-vs-direct path (iroh exposes which).
4. Roaming: hotspot to LAN mid-session; the sidecar reconnects, the
   client's existing sync backoff rides it out; record recovery time.
5. Allowlist enforcement: an unenrolled node id is refused (E2E
   negative test, Mac side).

## Out of scope

- Pi server, invite flows, key rotation, QR enrollment (phase 6).
- Self-hosted relay (recorded option; n0's relay is fine for the sweep).
- Any wataclient/wata-fb code change (loopback HTTP is the contract;
  if one becomes necessary, that is a finding for the plan's outcome,
  not a silent scope creep).
- launchd/persistent Mac service — `just server` + `just tunnel-serve`
  in a terminal is acceptable for the personal sweep; a service unit
  is deployment polish, phase 6.

## Verification

Milestone 3 is the acceptance bar: a voice message from the kitchen
Mac's server to a device on a hotspot in both directions, latencies
recorded in the plan outcome. `just ci` untouched (the sidecar is not
in the gate; a `tunnel-smoke` recipe exists for manual/scripted runs —
gating it needs network conditions ci cannot promise).
